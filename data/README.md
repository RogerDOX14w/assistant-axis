# Data Directory

Role and trait definitions used by the pipeline and analysis tools.
This extends Christina Lu's original dataset format with additional fields
and metadata. See [`data_analysis/`](../data_analysis/) for the scripts that
generate and process this data.

## Directory Structure

```
data/
├── goal_roles_and_traits.json   # Curated subsets of goal/nongoal roles and traits for experiments
├── goal_roles_and_traits_v1.json  # the April 2026 version, used by the 8slot extraction (record)
├── combination_scores.json      # incongruity scores for the 30x30 role+trait combos (+ _usage, _batches, .escalations)
├── extraction_questions.jsonl   # Questions used in pipeline Step 1
├── seed_queue.json              # Inventory and state of every candidate entity (Sep 2026 expansion; see below)
├── candidates/                  # Trait-gap platform: registry, filter runs, calibration/, metric_config.json (see the end)
├── external/                    # GIT-IGNORED downloads: hf/ (Hugging Face cache), wn/ (WordNet) (see the end)
├── roles/
│   ├── role_list.json           # {stem: description}, GENERATED by tools/sync_entity_lists.py (340 roles; instructions under role rubric V3 since 2026-10-03)
│   └── instructions/            # Per-role JSON files (341 files incl. default.json)
│       ├── <role>.json
│       ├── ROLES_TO_ADD.md       # Role-side work still to do: an index, then the open sections
│       └── ROLES_ADDED.md        # Finished role-side work, moved verbatim from ROLES_TO_ADD (incl. the V3 design log)
└── traits/
    ├── trait_list.json           # {stem: description}, GENERATED by tools/sync_entity_lists.py (932 traits, 2026-10-10)
    ├── antonym_check_history.jsonl  # append-only: every antonym check's candidates and the instructions it read
    └── instructions/             # Per-trait JSON files (932 files; 297 pairs recorded in `arrangement`, plus the squares, orthoplexes, rings, sequences, sets, maps and triangles); refused generations, if any, in `../generation_refusals.jsonl`
        ├── <trait>.json
        ├── TRAITS_TO_ADD.md      # Trait work still to do: an index, standing rulings, then the open sections
        ├── TRAITS_ADDED.md       # Finished trait work, moved verbatim from TRAITS_TO_ADD (audits, seeding plan, V2 design log)
        └── NEG_REGENERATION_NOTES.md  # Traits with misaligned neg instructions
```

`role_list.json` and `trait_list.json` are **generated views** of the
instruction files (since 2026-09-07): `{stem: description}`, sorted by stem,
one entry per instruction file with a non-empty `description`
(`roles/instructions/default.json` has none and is skipped).  No code reads
them; they are a one-file index for humans and LLMs.  After adding or editing
an instruction file run `uv run python tools/sync_entity_lists.py`;
`--check` exits 1 while they lag, and `tools/tests/test_sync_entity_lists.py`
fails.  Never hand-edit them.

## Instruction File Format

### Roles (`roles/instructions/<role>.json`)

```json
{
  "description": "One-sentence description of the role",
  "instruction": [
    {"pos": "System prompt inducing the role"}
  ],
  "questions": ["Question 1", "..."],
  "eval_prompt": "Evaluation template with {question} and {answer} slots"
}
```

Role instructions have only `pos` variants (no neg/opposite).

### Traits (`traits/instructions/<trait>.json`)

```json
{
  "positive_label": "trait_name",
  "negative_label": "antonym_name",
  "description": "One-sentence description of the trait",
  "instruction": [
    {"pos": "System prompt inducing the trait",
     "neg": "System prompt inducing the opposite"}
  ],
  "questions": ["Question 1", "..."],
  "eval_prompt": "Evaluation template with {question} and {answer} slots",
  "source": "optional: instrument the trait was imported from (see below)"
}
```

The `positive_label`, `negative_label`, and `description` fields were added
to Christina Lu's original format (which had only `instruction`, `questions`,
and `eval_prompt`). The `eval_prompt` is derived from `description` via a
fixed template; see `regenerate_trait_instructions.py`. If you use Roger's prompt for instruction geration, the `negative_label` is also passed in, giving tigher clustering instructions, especially the neg instructions.

The three JSON files that sit *beside* the `instructions/` directories
(`roles/regeneration_usage.json`, `traits/regeneration_usage.json`,
`traits/antonym_check_usage.json`) are cumulative API token-usage records
written by the regenerate and antonym scripts, not corpus entries; they are
kept out of `instructions/` so nothing that globs the corpus reads them.  `traits/antonym_check_history.jsonl` sits there for the same reason: one JSON
object per antonym check, never rewritten, holding the candidates the
generator named and the instruction set it read (written by
`data_analysis/seed_entities.py`; see `AGENT_NOTES.md` § "Keep every sample").

**Labels vs file names.** `positive_label` is the canonical *display* form
of the trait name and may contain hyphens, spaces and capitals
(`systems-thinker`, `traditional (Inglehart-Welzel)`); the file stem is
derived from it by `assistant_axis.entity_id.normalize_to_file_name`
(lowercase, hyphens and spaces to `_`, parentheses dropped, diacritics
folded to ASCII).  The
reverse direction is lossy, so
anything that renders a trait name to a human should call
`assistant_axis.entity_id.corpus_display_name(stem)`, which reads
`positive_label` back from this directory.  Traits imported from a named
instrument use the label convention `<pole> (<Standard>)`, parentheses
dropped in the stem, and record the
instrument in the optional `source` field (the description itself does not
name it).  A second optional field, `tags` (a list of strings, e.g.
`["physical"]`), marks traits that belong to a separate research track
and must not be assumed part of the main cohort; see
`instructions/TRAITS_TO_ADD.md` § "Physical-attribute traits".  Both
fields are carried forward unchanged by the regenerate scripts and
ignored by the pipeline.  A third optional field, `generator`, is
written (and overwritten) by the regenerate scripts since September 2026
on both roles and traits: which script and prompt style produced the
instructions, a short hash of the template text, the model, temperature,
thinking budget and date.  Files without it predate that change.

**Seed queue.** `seed_queue.json` (Sep 2026) is the inventory of every
candidate entity in `traits/instructions/TRAITS_TO_ADD.md` and
`roles/instructions/ROLES_TO_ADD.md` (finished sections since moved to the
`_ADDED` files beside them), one entry per entity with its chunk,
pairing, partner, description drafts and notes, final description and
status; `data_analysis/seed_entities.py` reads and updates it.  The two
markdown files remain the record of the reasoning; the queue is the record
of state.  Entries whose file already existed when the queue was built
carry status `exists`.

**Arrangements.** Roles and traits may carry an `arrangement` field, an
object `{"kind": ..., "members": [...]}` (or a list of them) recording
which set of same-type entities the file belongs to and its shape:
`singleton`, `pair`, `triangle`, `square`, `octahedron`, `N-orthoplex`,
`N-cube`, `ring`, `tree`, `map`, `sequence`, `set`.  Members are file
stems including the entity itself.  A missing field means not yet
classified.  Validate with `uv run python data_analysis/check_arrangements.py`;
full rules in `AGENT_NOTES.md` § "The `arrangement` field".  Spelling is US English throughout (`honor`, `laborer`): the
corpus is LLM input and the generators write US English.  Full convention:
`AGENT_NOTES.md` § "Standard-derived trait labels".

## `goal_roles_and_traits.json`

Curated lists of roles and traits partitioned by goal content (as determined
by `data_analysis/classify_goals.py`). Each of `roles` and `traits` has:

- **`goal`**: All 5 instructions scored 2 (clearly describes a goal)
- **`non_goal`**: All 5 instructions scored 0 (clearly no goal).  A candidate
  with four of five at 0 and none at 2 is resampled: each of its five
  instructions four more times at temperature 1, and it qualifies when every
  instruction's mean over the five samples is below 0.5 (Roger, 2026-10-10).

Traits are classified on their positive instructions; `physical`-tagged
traits stay out.  Three role instructions the classifier refuses in every try (the
virus's) are set by hand (Roger, 2026-10-10; `data_analysis/README.md`, `classify_goals.py`).  Items are ordered by priority tiers (randomized within each
tier); the pipeline reads the first 30 of each list by default:

| List | Tier 1 | Tier 2 | Tier 3 |
|---|---|---|---|
| `roles.goal` | 30 primary (varied) | 10 cluster duplicates | — |
| `roles.non_goal` | 30 most varied | 3 left over (2026-10-10: only 33 roles qualify) | — |
| `traits.goal` | 30 max goal-space variation | 10 (mostly moral-circle-size spectrum) | 26 default-side of pairs / redundant |
| `traits.non_goal` | 30 max persona-property variation | 10 nice-to-haves | 14 pair partners / redundant |

**Placed again on 2026-10-10** (pre-extraction W15) from a classification of
the whole corpus on its current texts (Opus 4.6, temperature 0; 10,976 of
10,979 instructions, $62; the borderline non-goal resample $16).  Every entry
of a list's previous top 30 that still qualified kept its place; every other
place went to the closest qualifying match to what was there (description
embeddings as a shortlist, tier 1 judged by meaning), earlier lower-tier
members counting like any other candidate.  `roles.non_goal` shrank because
the role rubric V3's instructions give many roles a commitment the classifier
reads as a weak goal; its tier 1 keeps the earlier job / non-job balance.
Draft, reasons and cosines:
`roger/pre_extraction_2026-10-09/w15/goal_tiers_draft.md`.

**Two generations, like the pair lists** (walk-through A3, 2026-10-12).
[`goal_roles_and_traits_v1.json`](goal_roles_and_traits_v1.json) is this file
as it was in April 2026 (`git show cac76b65:data/goal_roles_and_traits.json`,
byte-exact; unchanged until 3f6de81e on 2026-09-28; test
`results_analysis/tests/test_goal_file_generations.py`): the version the May
8slot extraction used and the record behind the `_v1` pair lists in
`roger/axis_judge_experiments/`.  Not the version just before W15
(`87d84fc^`): that one already has the September renames and near-duplicate
drops, so it names stems the 8slot data has no vector for
(`instrumentally_aligned_ai`, `cliquish`, ...) and lacks ones it has
(`aligned_artificial_intelligence`, `dramatic`, ...).  Both give the `_v1`
pair lists the same `goal_type`.  The
current pair lists' `goal_type` comes from this file (rebuilt with
`tools/build_pair_lists.py` the same day: `pair_list_goalnongoal.json` 37 → 26
pairs, 13 `goal_type` changes in `pair_list_clean.json`).  Scripts that work on
the 8slot data and read the goal lists default to the `_v1` file
(`results_analysis/canonical_angles/plots/ca1_plane_pre_post_shear.py`;
`tools/pick_base_personas.py` when given a `_v1` pair list).  Edit neither
`_v1` file.

For `traits.goal`, tier 1 prefers the less-HHH-default side of antonym pairs
(e.g., sadistic over compassionate) and spans distinct ethical frameworks,
moral-circle extremes, and alignment-relevant anti-traits. Tier 2 holds the
remaining moral-circle-size entries (may be worth revisiting whether the spectrum
needs much finer resolution). Tier 3 holds the more default-like / redundant traits.

## `combination_scores.json`

Incongruity scores for the role+trait instruction combinations of pipeline
step 1, generated by `data_analysis/score_combinations.py`. Each combination
gets one API call with all 5 index-matched instruction pairs scored
independently on a 0-3 scale (0 = fit well, 3 = very incongruous).  Pipeline
step 3 drops the prompt-variants scored 3 from combination judging.

Structure: `metadata`, `scores[]` (per-combo with `per_pair` reasoning and
`score_min`/`score_max`/`score_mean`, `pairs_sha256` of the texts scored,
`first_model`, and for an escalated combination `sonnet_scores` and every
rescore sample under `rescore_samples`), and `summary` with distribution.
Beside it: `combination_scores_usage.json` (cumulative usage),
`combination_scores_batches.json` (the Message Batches submitted) and
`combination_scores.escalations.jsonl` (each escalation, appended).

**Current run (2026-10-10, $15.96, batch):** the top 30 goal roles x 30
non-goal traits + 30 non-goal roles x 30 goal traits = 1,800 combinations, on
the current goal lists and instruction texts.  Sonnet 5.5 scored every
combination; the 340 with a pair at 2 or more (19%) were rescored three times
by Opus 5.5, keeping the median per pair (Roger: neither model takes
temperature, so three samples stand in for the April run's temperature 0; the
three agreed on 81% of pairs and two of three on the rest).  Rounded means
0 / 1 / 2 / 3: 865 / 794 / 141 / 0; per pair 4,235 / 3,975 / 787 / 3.  Sonnet
5.5 gave no 3 at all, and **only 3 of the 9,000 prompt-variants score 3** (in
`r_bodhisattva__temperamental` and `t_proofreader__unhelpful`), so step 3's
incongruity filter now drops almost nothing (the April scores dropped 29
variants among the 724 combinations both runs share).  Roger reviewed both
sides on 2026-10-10: the two current 3s are real, and of the 29 April 3s
([combination_3s_changed.md](../roger/pre_extraction_2026-10-09/combination_3s_changed.md))
many are roleplayable or were made by instruction texts since rewritten, so
the April scoring was oversensitive and the October scores stand.  The t_ combos still
score higher on average (mean 0.76) than the r_ combos (0.48).

**Before (April 2026, in git history at `cac76b6`):** 40 x 40 + 40 x 40 =
3,200 combinations, Sonnet 4 at temperature 0 with Opus 4.6 rescoring the
477 whose Sonnet score reached 2 (two more set by hand); 2187 / 862 / 134 / 17
at rounded mean 0 / 1 / 2 / 3, mean 0.38.  The 2,476 combinations outside the
current 30 x 30 lists were dropped from the file by the October run.

## Notes Files

- **`TRAITS_TO_ADD.md`**: what is still to do on the trait side: an index of
  the open items (before, at and after the extraction, the tangle pass, parked
  candidates), standing rulings for new traits, then the open sections.

- **`TRAITS_ADDED.md`**: the finished trait-side sections, moved verbatim
  from `TRAITS_TO_ADD.md` on 2026-10-09 with headings unchanged: the
  coverage audits and their "not added, and why" lists, the seeding plan,
  the trait generator V2 design log.  Historical text; its TODO markers are
  not live.

- **`ROLES_TO_ADD.md`** / **`ROLES_ADDED.md`** (in `roles/instructions/`):
  the same split for roles: the process for adding a role and the open role
  items; the finished audits and the role rubric V3 design log.

- **`NEG_REGENERATION_NOTES.md`**: Traits where the neg instructions don't
  match the corrected `negative_label` — typically due to RLHF influence
  during generation. Documents the misalignment, correct direction, and
  likely cause for each.

## Trait-gap platform: candidates, calibration, external downloads (Oct 2026)

The trait-gap platform (plans and reports in
[`reports/trait_gap_generation/`](../reports/trait_gap_generation/)) keeps its
data under `data/candidates/` and `data/external/`.  Nothing here is read by the
persona pipeline, and nothing the platform writes touches `traits/` or
`roles/`.

- **[`candidates/calibration/`](candidates/calibration/)** (tracked): the M2
  metric calibration, written by
  [`calibrate_metric.py`](../data_analysis/gap_generation/calibrate_metric.py).
  Hand-checked inputs: [`labelled_pairs.json`](candidates/calibration/labelled_pairs.json)
  (seeded by `labels.py`, curated in `labelled_pairs_curation.json`),
  [`contrast_cuts.json`](candidates/calibration/contrast_cuts.json) with
  `contrast_cut_overrides.json`, and Roger's marks
  ([`contrast_marks_roger.json`](candidates/calibration/contrast_marks_roger.json)).
  Outputs of the pilot and rounds 2-3 (`loo_metrics.json`, `loo_table.md`,
  `thresholds.json`, `hubness.json`, `contrast_ablation.json`,
  `drop_or_merge.md`, `nn_hist_<model>.png`, `summary.json`,
  `paraphrase_metrics.json`), the Haiku paraphrase sets
  (`paraphrases.json`, `paraphrases_plain.json`, `paraphrases_terse.json`;
  each records under `sources` the sha256 of the label and description every
  paraphrase was written from, so one of a since-changed text is regenerated),
  round 4's retrieval test
  ([`retrieval_round4.json`](candidates/calibration/retrieval_round4.json) and
  `.md`), run records (`run.json` for round 3's full run, `run_round4*.json`,
  `run_write_config*.json`) with their logs, and
  [`usage.json`](candidates/calibration/usage.json), cumulative over every run
  (with `usage_notes.md` for the one estimated entry).  The JSON outputs carry
  the `json_metadata` provenance envelope.  The readout is
  [`pilot_m2_readout.md`](../reports/trait_gap_generation/pilot_m2_readout.md).
- **[`candidates/metric_config.json`](candidates/metric_config.json)**
  (tracked): the settings M3 reads (`assistant_axis.gapgen.MetricConfig.load()`),
  written by `calibrate_metric.py --write-config` (task 19, 2026-10-02) from
  the recorded calibration outputs, with the provenance envelope.  It records
  Roger's M2 final settings: the live model (OpenAI `text-embedding-3-large`),
  EmbeddingGemma as an inactive fallback with its own numbers, bge dropped;
  the covered setting (`w20`, centred on the fixed corpus mean, cosine,
  retrieve k = 10, with recall@1/5/10/20 per query source; `t_hi`/`t_lo` kept
  as information only); the directional setting (`w20`, centred, K = 10,
  provisional); and the drift canary (8 fixed texts every embedding run
  re-embeds and compares with the cache, warning below cosine 0.999).  Never
  edit it by hand; rewrite it with `--write-config` (its `config_version` is
  the date).
- **Packed record files** (2026-10-14; GitHub refuses a file over 100 MB).
  A run's record files may live gzip-compressed beside or instead of their
  plain form, about 6x smaller, and every reader of the platform reads them
  through [`records.py`](../assistant_axis/gapgen/records.py) as it reads the
  plain files.  Two kinds, by file name: **logs** (`responses.jsonl`, appended
  to while a run is live) read as `X.gz` followed by `X`, so a resume of a
  packed run appends to a fresh plain `X`; **snapshots** (`results.jsonl`,
  `graph.json`, `readings.jsonl`, `matches.jsonl`, rewritten whole) read the
  plain `X` when it exists, else `X.gz`.
  [`pack_records.py`](../data_analysis/gap_generation/pack_records.py) packs
  them (`--dry-run` lists every file of `--min-mb`, default 50, or more under
  `candidates/`; `--path P` packs one file); it refuses any other file name,
  a run holding its lock, and a log whose plain file repeats its `.gz`, and
  deletes the plain file only after the new `.gz` decompresses to exactly the
  content it read.  Pack only a run that has ended, then commit the `.gz` with
  the plain file's deletion.  The registry log `registry.jsonl` and the review
  app's `decisions.jsonl` are not packed (the registry's tracked copy is its
  gzipped snapshot).
- **`candidates/cache/embeddings/`** (git-ignored): the embedding cache,
  one `<model_tag>.npz` per model keyed by sha256 of the text, plus
  `manifest.json`; written by `embed.embed_texts` and read by every
  calibration run, so a rerun costs nothing.  Deleting it means paying to
  re-embed (OpenAI: cents).
- **`external/hf/`** (git-ignored, inside `external/`): the Hugging Face cache.
  Importing `assistant_axis.gapgen` points `HF_HOME` here, so no model is ever
  read from or written to the home directory.  M2's two local models were
  fetched by `setup_external.py --hf-model` with allow-listed files only:
  `BAAI/bge-large-en-v1.5` (1.34 GB, dropped from use on 2026-10-02) and
  `google/embeddinggemma-300m` (1.27 GB, the inactive fallback).  Other
  platform work has placed small Qwen and Gemma chat models here too.
  **Deleted 2026-10-21 to free disk (Roger: delete what we are probably done
  with, redownload if that proves wrong):** both M2 models and their caches
  (`local_*.npz` and their `manifest.json` entries), `Qwen/Qwen3-8B-Base`
  (15 GB, plan 03; needed again only for its wave 2), and the three
  masked-LM models of plan 04 (ModernBERT-large, roberta-large,
  bert-large-cased-whole-word-masking, about 4 GB) with
  `candidates/cache/masked_lm/`.  Each comes back with
  `setup_external.py --hf-model ID` (or the generator's own fetch); the
  masked-LM aggregates are recomputed locally on the next run.
  `external/wn/` (also git-ignored) holds the Open English WordNet 2024
  database used by the M1 filter.
