# Working with Jev: what we have noticed so far (2026-11-05)

Written for Roger and for later Claudes, before they ask Jev anything.  **Read this as clues, not as a guide.**  Everything below comes from one small test: 61 axes of the May corpus, judged in November 2026 with `jev-1.14.0`, mostly by one session over two days, plus a response-judging pilot by another.  Several findings rest on a few dozen axes, one did not replicate on held-out axes, and nothing has been checked on the October corpus.  Where a number is given it is the one we saw, with its setting; where a reason is given it is a guess.  The results themselves are in [`jev_judging.md`](./jev_judging.md) (descriptions and instructions) and [`response_judging_plan.md`](./response_judging_plan.md) § 4b (responses).

## 1. What Jev is, as we have used it

Jev is TypeSafe AI's model, served at `POST https://api.typesafe.ai/v1/systemone`.  The facts below are from TypeSafe's documentation, read on 2026-11-04 and again on 2026-11-05 with the page named beside each fact, and from our own probes.  The pages are Markdown, and the index of all of them is [llms.txt](https://docs.typesafe.ai/llms.txt), which TypeSafe's [page for coding agents](https://docs.typesafe.ai/introduction/coding-agents.md) says to fetch first; a Claude can read any of them with WebFetch.  The ones that matter here: the [API reference](https://docs.typesafe.ai/api/system-one.md) (request and reply shapes; the [OpenAPI spec](https://api.typesafe.ai/openapi.json) is the formal version), [Models](https://docs.typesafe.ai/models.md) (versions, context length, pricing, rate limits), [Request rules and errors](https://docs.typesafe.ai/api/errors.md), [State](https://docs.typesafe.ai/concepts/state.md), the question types [Noul](https://docs.typesafe.ai/primitives/noul.md), [Score](https://docs.typesafe.ai/primitives/score.md) and [Choice](https://docs.typesafe.ai/primitives/choice.md), [Confidence](https://docs.typesafe.ai/confidence.md), [Model jaggedness](https://docs.typesafe.ai/model-jaggedness.md) (the known weaknesses; the page most worth reading before designing a question) and the [model changelog](https://docs.typesafe.ai/changelog.md).  TypeSafe also publishes an [agent skill](https://docs.typesafe.ai/agent-skill.md) for Claude Code and other agents (`claude plugin marketplace add typesafe-ai/skills`, then `claude plugin install typesafe@typesafe-ai`); nobody here has installed it, and our tools call the HTTP API directly rather than through the [Python SDK](https://docs.typesafe.ai/sdk/python.md).

- **One state, many questions.**  A request carries a `state` (a string, a JSON object or an array of text) and a dictionary of typed `questions`, each with `instructions` and, for most types, `criteria`.  Jev reads the state once and answers every question against it independently.  Each question sees all of the state and none of the other questions ([State](https://docs.typesafe.ai/concepts/state.md): "All questions see the same state and are evaluated independently").  TypeSafe's own measurement of this shape is the [parallel questions cookbook](https://docs.typesafe.ai/cookbooks/parallel_questions.md): thirteen questions about one document in one call gave the same answers as one call each, about 12x cheaper and 10x faster.
- **Billing is on input only.**  $0.042 per million input tokens; output is free ([Models](https://docs.typesafe.ai/models.md): "You pay per input token.  Output tokens are free"; the reply's `usage.output_tokens` is "currently free of charge" in the [API reference](https://docs.typesafe.ai/api/system-one.md), so the price could change).  The state is billed once per request, and every question's text is billed too.  So a long state shared by many short questions is the cheap shape, and a long question repeated for every item is the dear one.
- **Limits.**  64k tokens per request (state plus all questions) and 32k per question (state plus that question); no limit on the number of questions ([Models](https://docs.typesafe.ai/models.md) § "Context length").  A `TypeSafe-Danger-Zone-Long-Context: true` header raises both to 262k, at the same price, "slower and less accurate than staying within the default limits, so turn it on only for requests that need it" (same page); we have not used it.  A request over the limit is an HTTP 400 with `max_tokens_exceeded` ([Request rules and errors](https://docs.typesafe.ai/api/errors.md), which also caps the body at 32 MiB and nesting at 64 levels, and takes gzip or zstd bodies).
- **No knobs.**  There is no temperature, no reasoning or thinking output, no batch API and no off-peak tier.  The API has `/v1/models` and `/v1/systemone` only ([OpenAPI spec](https://api.typesafe.ai/openapi.json)).  The [introduction](https://docs.typesafe.ai/introduction.md) puts it as "No text generation, no parsing", and says "adding questions barely changes the response time"; the [AI primer](https://docs.typesafe.ai/introduction/machine-learning-primer.md) describes the model as trained (by RLCD) to return decisions and calibrated probabilities rather than generated text.
- **Question types we used.**  [`noul`](https://docs.typesafe.ai/primitives/noul.md): yes/no, answered as a probability of yes.  [`score`](https://docs.typesafe.ai/primitives/score.md): 2 to 10 ordered levels, each a criterion string, answered with a probability over the levels and a point `score`.  [`choice`](https://docs.typesafe.ai/primitives/choice.md): up to 255 options, answered with a probability per option.  The [Model jaggedness](https://docs.typesafe.ai/model-jaggedness.md) page warns that "Jev's score levels are weak in numerical calibration" and says not to read a Score's expectation as the exact magnitude of something between two levels (§ "Math using score").  Pairwise and three-question variants are our own constructions on top of `noul`.
- **Versions.**  `GET /v1/models` ([List models](https://docs.typesafe.ai/api/list-models.md)) lists only the aliases `jev-latest` and `jev-preview`, but [Models](https://docs.typesafe.ai/models.md) says a versioned ID such as `jev-1.14.0` is "accepted by the `model` field whether or not they appear in the list", and each reply's `model` field "gives the versioned ID that answered".  An alias "moves when a new release ships, so its answers can change without any change to your code"; the page's own advice is to send the version's ID once thresholds have been tuned against it.  A malformed or unknown ID is an HTTP 400 (our probe; the docs do not say).  Jev 1.14 is dated 2026-10-14 in the [model changelog](https://docs.typesafe.ai/changelog.md), its only entry; on 2026-11-04 `jev-1.13.0` was still served, and no retirement policy is published.  (The model cards' `release_date` fields on 2026-11-05: `jev-preview` 2026-10-14, `jev-latest` 2026-10-22, which looks like when each alias moved to 1.14.)  Our tools request `jev-1.14.0` and refuse to write a cell if any answer comes from another version.
- **Rate limits** are "set per organization", "measured in tokens per second and requests per second", and shown only in the [developer console](https://console.typesafe.ai/rate-limits); a request over either is a 429, to be retried with exponential backoff, following the `retry-after` header when there is one ([Models](https://docs.typesafe.ai/models.md) § "Rate limits", [Request rules and errors](https://docs.typesafe.ai/api/errors.md)); higher limits are by [request form](https://support.typesafe.ai/forms/rate-limit-increase-request).  We never looked ours up; the console is behind the account login, so the figures are a question for Roger, not something a Claude can fetch.  Our tools ran at 24 (entities) and 32 (responses) requests in flight and finished without a fatal failure, but they do not log retries, so we cannot say how many 429s there were.
- **The reply** carries `model` ("may differ from the alias supplied in the request"), `answers` keyed by our question ids, and `usage` with `input_tokens` and `output_tokens` ([API reference](https://docs.typesafe.ai/api/system-one.md)).  For `noul` an answer is `{"type": "noul", "noul": 0.18}`.  Score and Choice answers also carry a `confidence`, which [Confidence](https://docs.typesafe.ai/confidence.md) describes as a measure of how concentrated the probabilities are, not of whether the answer is right; we have not used it.

## 2. Asking: what seemed to help

These are the clues from [`jev_judging.md`](./jev_judging.md) § "What was tried", measured on the 30 development axes with one pass in the axis's own order, except where said.

- **Put many items in the state and ask one question per item.**  Twenty entities a request beat one a request by about +0.013 ρ, at a third of the cost; one entity per request was the worst Noul design we tried.  Our state is a JSON object: a one-line `task`, the `axis` with its two ends and their descriptions, and numbered `entries`, each with its name, kind and text.  Each question names its entry number and name.  (The [Model jaggedness](https://docs.typesafe.ai/model-jaggedness.md) page warns that "accuracy falls as the state grows with content unrelated to the decision", and [How to build](https://docs.typesafe.ai/concepts/how-to-build-with-system-one.md) says to "include only the context relevant to the current questions".  Our states grow with related content, the other entities on the same axis, and within the 64k limit accuracy rose with batch size, not fell.)
- **A yes/no question did as well as or better than a scale.**  The single Noul ("is it nearer the *pos* end of the axis than the *neg* end?"), read as P(yes), beat Score with five or ten levels and Choice with 11 or 21 options at the same batch size.  Read the probabilities, not the point value: Score with five levels scored 0.671 as the expected level and 0.681 as the probability mass on the second pole's side.  A rank correlation does not need calibration, which is the one thing the docs say Score lacks.
- **Every level or option must stand alone.**  Jev reads each criterion on its own, without its neighbours or its number ([Score](https://docs.typesafe.ai/primitives/score.md): "Every level is evaluated separately.  The model doesn't see a level's number or its neighbours"; its example of levels that are only numbers has the probability split between the ends), so a level that says only "somewhat" is meaningless; ours each name both ends ("Somewhat *pos*: leans toward *pos* more than toward *neg*").  Output is free, so long criteria cost nothing; long question text does.
- **Three questions per item ("strong") and all-pairs comparisons added nothing** over the single Noul, and the pairs cost six times as much.  A pairwise ring (each entry against its neighbours) was not better either.
- **The relative wording ("nearer the *pos* end than most of the other entries are?") was the best arm on the development axes, and its gain did not replicate.**  It rose with batch size (0.698 at 10 entries, 0.711 at 20, 0.724 at 160, 0.7245 at 290) and won among about twenty arms on dev30; on the 31 held-out axes it equalled the plain Noul at 20 (−0.001 descriptions, −0.002 instructions).  We kept it because it is no worse and batches cheaply, but the lesson is the general one: an arm picked among many on one half of the axes should be read on the other half before it is believed.  The production cells are this design at 160 entities a request (`jd_noul_relative_n160`, `ji_noul_relative_n160`).
  - *Added 2026-11-05, after the response finding below (Roger: was the like tried on descriptions and instructions?).*  **The plain Noul was Jev's first design on entities, and there the relative wording keeps a small lead.**  The plain question ("nearer the *pos* end than the *neg* end?", each entry judged on its own) was run at 1, 10, 20 and 40 entities a request, the relative one at 10 to 290; the plain one was never run at 160.  On all 61 axes, balanced, the plain Noul at 20 trails the relative at 160 by 0.0125 [0.006, 0.020] on descriptions (two passes, 0.692 against 0.705 over the 12 variants; 0.744 against 0.758 at slot 6, layer 25, raw) and by 0.010 [0.005, 0.017] on instructions (one pass of five rounds, 0.715 against 0.725); in the axis's own order the gaps are 0.008 and 0.004, with intervals through zero.  At the same batch size on dev30 the two wordings are level (at 10 the plain is +0.004, at 20 −0.006, at 40 −0.008, all within noise), and the plain one's batch curve is flatter (0.648 at 1, 0.658 at 10, 0.660 at 20, 0.662 at 40, against the relative's 0.654 at 10, 0.666 at 20, 0.670 at 40, 0.673 at 80, 0.676 at 160), so the relative question seems to be the one that gains from a large batch, which is what one would expect of a question about the batch.  The gap is concentrated: the plain wording is far worse on [descriptive](../../data/traits/instructions/descriptive.json) vs [prescriptive](../../data/traits/instructions/prescriptive.json) (−0.12 to −0.21), [ecocentric](../../data/traits/instructions/ecocentric.json) vs [anthropocentric](../../data/traits/instructions/anthropocentric.json) (−0.09 to −0.14, the axis it also collapsed on in the response pilot) and [religious](../../data/traits/instructions/religious.json) vs [secular](../../data/traits/instructions/secular.json) (−0.05 to −0.09), and better on [systems_thinker](../../data/traits/instructions/systems_thinker.json) vs [analytical](../../data/traits/instructions/analytical.json) (+0.04 to +0.10) and [concise](../../data/traits/instructions/concise.json) vs [verbose](../../data/traits/instructions/verbose.json) (+0.035 to +0.08); a wording can move one axis by 0.1 or more either way.  So the response finding does not carry to entities, and the guess made for responses stands: a batch of 160 unrelated entities gives "than most of the others" a real reference set, and twenty answers to one question does not.  Evidence: [`jev_plain_vs_relative.py`](../../scripts/jev_plain_vs_relative.py) and its [JSON](../../roger/axis_judge_experiments/jev_wording/jev_plain_vs_relative.json), from the cells on disk, no new judging.  Not run: the plain Noul at 160 (about $3 for both modes, two passes), and the responses' other feature, several axes in one request with the axis in the question rather than in the state.
- **Pole order matters more to Jev than sampling does.**  An exact rerun agrees with itself at 0.997 (34% of answers identical to two decimals), the same entities in other batches at 0.976, and the opposite pole order at only 0.917 to 0.930.  (TypeSafe documents an order effect of its own for Choice: "the order of a Choice's options can affect the answer, and Jev leans toward the option that comes first", [Model jaggedness](https://docs.typesafe.ai/model-jaggedness.md) § "Choice option order".)  So a second pass is worth having only in the opposite direction (+0.010 on descriptions; +0.003 same-order; a plain rerun +0.0003).  Roger's rule that no judging runs in one fixed order applies to Jev as it does to the others; Jev shows no moral-valence lift from the order (own order minus balanced: −0.001 and 0.000, against Luna's +0.013 and +0.008), so balancing costs it nothing.
- **Instructions:** one instruction per entity per request, the five instructions over five rounds, each round's direction from Jev's column of Roger's table (`judge_tier_cost_eval.INSTRUCTION_DIRECTIONS`; B A B A d).  A balanced one-pass Jev already alternates directions over the five instructions, so a second pass adds only +0.0009 there.

## 3. Reading the answers

- **Noul probabilities come at two decimals**, between 0.03 and 0.97 in our 35,000 answers per pass, never 0 or 1, and skewed low: on the relative question ("nearer than most of the others?"), whose honest mean would be about 0.5, the mean is 0.43 and only 1% of answers are exactly 0.5.  We use the values only through Spearman ranks, where neither the skew nor the coarseness has shown any effect.  Nothing here says what the probabilities mean absolutely.  The [Noul](https://docs.typesafe.ai/primitives/noul.md) page says the value is "the answer and the certainty in one", suggests 0.7 and 0.3 as starting thresholds, and warns that a Noul value "is not a scale of the thing you asked about": if the question is about degree, "the value does not measure the degree".  We use it as a degree anyway, through ranks, and on this test it ranked entities better than Score, the type built for degree; why is open.
- **Scores are 100 × P(yes)** in our cells, mapped back (100 − v) when the request showed the axis reversed; every answer record says which way its request went.
- **Keep the whole reply.**  Our tools log every reply, probabilities included, under `roger/axis_judge_experiments/_tier_eval_jev/<label>/answers.jsonl`, with the run's settings in a header line.  A stopped run resumes from it, a run under other settings is refused, and another way of reading a score out of the same answers costs nothing.  (The `at` timestamps in those logs are rewritten on resume, so they do not record wall time.)
  - *Added 2026-11-06.*  **The logs are most of what a Jev run leaves on disk, and they compress about sevenfold.**  The 64 entity cells' answer logs come to 231 MB and the response pilot's to 673 MB, which mattered on the day the laptop ran out of disk; gzip takes a 2.0 MB entity log to 0.29 MB and a 51 MB response log to 6.4 MB.  Neither tool reads a compressed log, so a cell whose log is gzipped can neither resume nor be re-read until it is unpacked: compress only a cell that is finished and not about to be re-read, or teach the tools to open `.gz` first.

## 4. Quality: where it stood on this test

Balanced cells, 61 axes, ρ at slot 6, layer 25, raw unless said; the full tables are in [`jev_judging.md`](./jev_judging.md).

- **Descriptions:** Jev alone at one pass 0.745 against Luna's 0.709, at $0.004 an axis against $0.011; at two passes 0.758 at $0.008, on the cost frontier in 12 of 12 projection variants.  **Instructions:** 0.781 at one pass against Luna's 0.768, at $0.021 against $0.050; frontier in 12 of 12.  So on this corpus it was the best single judge we had, and the cheapest.
- **It is in the standard blend at 4 : 3 : 3 : 12 (Luna : Haiku : Gemini : Jev)** in both modes, a weight chosen for resilience rather than fitted to the mean; the fit gave 24, which made the blend about 68% Jev in effect (§ "Jev's weight: 12, for resilience" of [`jev_judging.md`](./jev_judging.md)).
- **Its bad axes are one class, and stable.**  Jev trails the other three judges on style axes: [precise](../../data/traits/instructions/precise.json) vs [vague](../../data/traits/instructions/vague.json) by −0.105 in both modes, then [proactive](../../data/traits/instructions/proactive.json) vs [reactive](../../data/traits/instructions/reactive.json), [concise](../../data/traits/instructions/concise.json) vs [verbose](../../data/traits/instructions/verbose.json), [superficial](../../data/traits/instructions/superficial.json) vs [thorough](../../data/traits/instructions/thorough.json), [accessible](../../data/traits/instructions/accessible.json) vs [esoteric](../../data/traits/instructions/esoteric.json).  The gap on pass 1 predicts the gap on pass 2 across axes (0.96 on instructions), so this is the model, not noise.  A guess worth testing: our question asks about "how the person described typically behaves, what they value and what they are associated with", which may steer Jev away from how someone *expresses* themselves; a wording that names style might close some of it.  Its best axes by the same measure: [ecocentric](../../data/traits/instructions/ecocentric.json) vs [anthropocentric](../../data/traits/instructions/anthropocentric.json) (+0.08 to +0.09 over the trio), [introverted](../../data/traits/instructions/introverted.json) vs [extroverted](../../data/traits/instructions/extroverted.json), [casual](../../data/traits/instructions/casual.json) vs [formal](../../data/traits/instructions/formal.json).
- **It adds less valence than the LLM judges.**  Beyond what the whitened projections carry, Luna's scores add a good-versus-bad component (partial correlation +0.077), Gemini's and Haiku's less, Jev's barely (+0.010).  Roger's reading: Jev "is less focused specifically on that aspect of questions that are somewhat entangled with it".  It is also why Jev gains more than the others from soft whitening of the projections.
- **On responses it was weaker, and not cheaper, in the first design.**  One answer per request, every axis as a Score question: 0.55 to 0.58 against Luna's 0.68 on a ninth of six axes' responses, whatever the level count (3, 5, 7, 10, or Choice of 11), collapsing on ecocentric vs anthropocentric (0.17 to 0.44 against Luna's 0.77).  A plausible reason: unlike the percentile rubrics, that design showed Jev one answer at a time with nothing to calibrate against, and each axis's question text was billed per request.  A second design batches 20 answers and several axes into one state and asks the relative Noul per answer and axis; a preliminary reading on 12 axes put it at 0.696 against Luna's 0.716, with a Luna 4 : Jev 2 blend +0.011 over Luna alone.  That figure and the comparison of question types for it are unfinished work of the response-judging session; do not quote them as results.

## 5. Limitations and quirks

- No temperature, no reasoning, no batch discount, no Flex: the price is the price, and a rerun under the same settings is nearly a no-op (0.997 agreement).
- An alias in the `model` field can change answers under you; pin the version.  On 2026-11-04 one session concluded from `/v1/models` alone that versions could not be pinned and switched the drivers to `jev-latest` for a few hours; a live probe of the versioned ID would have settled it in a minute.
- The pages we read say nothing about languages beyond that Jev "reads natural-language text" ([Models](https://docs.typesafe.ai/models.md)); the examples are in English, and [Model jaggedness](https://docs.typesafe.ai/model-jaggedness.md) notes that colours as hex values "underperform compared to those using the English names".  Our corpus is English, so the question never arose.  (The first draft of this line said the docs call English the primary language; no such sentence was found on 2026-11-05.)
- Jev reads each criterion on its own and has no view of the other questions, so a scale cannot be described once and referred to; say it in every criterion.
- The question text is billed per question.  Response judging with one axis per request paid about $0.38 an axis on a ninth of the responses, above a cached-prefix LLM judge; batching axes into the state is what makes it cheap.
- We have not measured latency or throughput (the logs on disk were rewritten by resumes), the rate limits, or long-context mode.
- A 160-entity description request was about 27k input tokens and 3k output tokens; an instruction request about 28k.  That is close to half the per-request limit, and the 32k per-question limit was never approached.
- *Added 2026-11-06.*  **What an entity judgement costs, and so what the October corpus would.**  One pass of descriptions on one axis of the May corpus (580 entities in 4 requests of 160, 99k input tokens) cost $0.0042, and one round of instructions the same, so a five-round pass $0.021: about 170 input tokens and $0.000007 per entity judgement, the state's share of each.  The October corpus has about 1,270 entities (932 traits and 340 roles in [`data/`](../../data/) today), 2.2 times as many, so if its texts run about as long as May's the settled two-pass designs would cost about $0.018 an axis for descriptions and $0.09 for instructions, about $22 for 200 axes in both modes, in 16 and 80 requests an axis.  That is arithmetic from the May price, not a measurement: October's instructions may be longer, the rate limits have not been met at that scale, and nothing has been judged on that corpus.

## 6. Tooling in this repository

- [`scripts/judge_jev_entities.py`](../../scripts/judge_jev_entities.py): descriptions and instructions, the four wordings (`base`, `rank`, `strong`, `relative`), the four question types, balanced directions, the answer log and resume, `--expect_model`, `usage.json` with `price_for_model("jev-1.14.0")`.  Run by [`judge_descriptions.py`](../../results_analysis/judge_descriptions.py) and [`judge_instruction_grid.py`](../../scripts/judge_instruction_grid.py) `--design rounds`.  Tests: [`test_judge_jev_entities.py`](../../scripts/tests/test_judge_jev_entities.py) and the jev_entities tests in [`test_judge_tier_cost_eval.py`](../../results_analysis/tests/test_judge_tier_cost_eval.py).
  - *Added 2026-11-06.*  **To read a request as Jev receives it, run the tool with `--dry_run`**: it builds every request, logs how many axes, entity judgements and requests there are with the estimated cost, prints the first request's body (its first 6,000 characters) and sends nothing.  Read that, not the template, before changing a wording: the state and the questions are where a mismatch between the instructions and the data shows, as the rendered-prompt rule in [AGENT_NOTES.md](../../AGENT_NOTES.md) says.
- [`scripts/judge_responses_jev.py`](../../scripts/judge_responses_jev.py): responses, the one-answer Score and Choice designs and the batched relative design; the HTTP client and retry policy both tools share (retries on 429, 5xx and 529 at 2, 5, 15, 45 and 120 s, which is what [Request rules and errors](https://docs.typesafe.ai/api/errors.md) asks for, "exponential backoff instead of retrying immediately", and what the SDKs do by default; any other 4xx raises as a bug in the call).
  - *Added 2026-11-06.*  **A budget or refusal check before the concurrency gate stops nothing.**  Both tools start a coroutine for every request at once and let `--max_in_flight` of them hold a slot at a time.  Until 2026-11-04 the budget check and the stop-on-fatal-error check ran before the slot was taken, so every queued request had passed them before the first reply came back, and neither `--budget_usd` nor a fatal 4xx ever stopped a request (found by the response-judging session; fixed in both tools, where the checks now run once a request holds its slot).  Any asyncio driver with a semaphore can have the same shape: look at where the gate is before trusting a cap, and test a cap by setting it below one request's cost.
- The key is `TYPESAFE_API_KEY`, from the environment or `.env`, sent as `Authorization: Bearer` ([quick start](https://docs.typesafe.ai/introduction/quickstart.md)); never read the file, print the key or write it anywhere.
- Costs so far: about $16 of Jev credit for everything in [`jev_judging.md`](./jev_judging.md), against $27 of trio judging for the matching balanced cells.

## 7. Not yet tested

Questions this test leaves open, in no order: whether the relative wording's gain over the plain Noul reappears on the October corpus or stays within noise; whether a style-aware question wording helps the style axes; the plain Noul at 160 entities a request, the one batch size it was never run at on descriptions and instructions (§ 2); whether the order of entries in the state matters (we shuffle by seed), and whether the option-order effect TypeSafe documents for Choice bears on our Choice arms, whose options were the scale points in order; what the rate limits are and how fast a full corpus can be judged; whether long-context mode at 262k lets a whole axis go in one request and what it costs in accuracy; what Jev's probabilities mean on an absolute scale; and the response designs above.  None of these is scheduled; add to this list rather than to the clues above until something has been measured.
