# Gate audits: what each gate in the gap-filling work throws away, and whether it should

Written 2026-10-12 on Roger's instruction, after the IPIP consensus gate turned out to discard two thirds of
the item pool at g600 (and 92% at g150) while the discarded clusters were, on a sample, as good as the kept
ones: "for any gate that is throwing away more than say 3% of our candidates, we need to look at a sample of
what it's actually throwing away, and how well that fits the original intent.  What are its false-positive and
false-negative rates?  Is it doing what was intended, about as well as possible?  Or could it be improved?  Or
is it mostly not doing what was intended, and is unfixable?"

A **gate** here is any rule in the candidate pipeline that removes, holds or routes candidates without a
human reading them.  One Opus agent audits each gate below and writes its report beside this file
(`<gate>.md`, the names in the table).  The review that produced this list is recorded in
[escalations.md](../escalations.md); the terms (M1, M3, R1, the registry, the review app) are defined there.

## The audit, the same for every gate

1. **The rule, from the code**, with `file:line`: what is compared with what, every constant, every exception, and what happens to a candidate that fails (dropped, held on a list, routed to a probe or a pass).
2. **The intent, from the plan or QUESTIONS entry that set it**, quoted.  Where the number was set without a recorded derivation, say so.
3. **The recorded discard**: counts per run from the records named above (the run's `evaluation.json` / `submit_report.json`, the registry blocks, the run directories), reproduced by the agent, not copied from this table.
4. **A sample, read by the agent**: at least 60 discarded (or held, or unread) items and at least 40 kept ones, stratified across the runs the gate has seen, drawn with a recorded seed.  For each item the agent writes a one-line verdict against the intent — not against the rule — and says what its judgment rests on (the gloss, the item texts, the corpus trait it names, a reference label where one exists).  The agent's verdicts are its own reading and are labelled as such; where reference labels exist (the M1 validation set, Roger's review decisions, the M3 cover audit) they are used first and the agent's reading second.
5. **Rates**: the false-negative rate (discarded but fits the intent) and the false-positive rate (kept but does not), each with a 95% binomial interval on the sample, and the implied counts over the full run.
6. **The verdict**, one of: *doing what was intended, about as well as possible*; *doing what was intended but improvable* (how, and the expected change in the two rates); *mostly not doing what was intended* (fixable: how; or not: why).  For a threshold, whether the data support the value, and whether it should depend on something it ignores (the IPIP gate: cluster size; the count floor: the sample size; the Zipf line: the generator's own frequency scale).
7. **Proposals**, each with its cost (most are $0; a re-judge is cents per candidate) and the evidence that would settle it.

## Rules for the agents

- Read-only: no code or data edits, no git operations, no paid calls (`--dry-run` only), nothing read outside the repository and `/tmp/claude-501/`; never `.env`.  The report is the only file written, under this directory.
- Every file mentioned in a report is a markdown link relative to this directory; a trait or role stem that has an instruction file links to it.  Project terms are defined on first use or linked to [escalations.md](../escalations.md)'s terms block.
- Sample tables go in the report in full (they are the evidence), with the seed and the selection rule.
